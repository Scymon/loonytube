## New findings

### P2 — Username-based superadmin bootstrap still in `roles.sql`; orphaned `security` branch never landed (NEW)
**Evidence:** `supabase/roles.sql:134` — `update public.profiles set role = 'superadmin' where username = 'david';`. An unmerged branch `security` (`372b653`, 2026-06-20) fixed exactly this (replacing it with a commented UUID-based template and the warning "a malicious user could register the username before you run this"), tightened the stream-webhook replay window from 600s to 60s, and added a security.txt route + honeypot files — none of it is in HEAD, `dev`, or `main`.
**Impact:** Low in the current deployment (the bootstrap has presumably already run; platform is invite-gated), but any fresh environment set up from the README's migration list re-runs this file, and a squatted `david` username becomes superadmin. The webhook's current 10-minute replay window (`stream-webhook/route.ts:38–41`, constant-time HMAC verified) is acceptable but looser than the branch intended.
**Definition of done:** `roles.sql` bootstrap converted to the commented UUID template; decide per-hunk whether to cherry-pick or discard the rest of the `security` branch, then delete the branch so it stops being invisible latent work.
**Size:** S. **Status:** new, ready.

### Note — Styleguide tab is superadmin-only in UI, admin-writable at the DB
`AdminShell.tsx:40` marks the tab `superOnly`, but the theme lives in `site_config`, whose update policy is `public.is_admin()` (admin **or** superadmin). Any admin can write `theme` via the REST API despite not seeing the tab. Harmless today (validation makes bad values inert; admins are trusted); worth a one-line `is_superadmin()` check only if the roles are meant to differ. Not tracked as a finding.
